# Minecraft Pack Builder: High-Level Product Specification

Дата: 2026-06-23

## 1. Product Summary

Minecraft Pack Builder - кроссплатформенное десктопное приложение для обычного Minecraft-игрока, который хочет проектировать строительные схемы под конкретный CurseForge-модпак с помощью внешнего AI-инструмента.

Приложение не поставляется с собственной AI-моделью и не генерирует постройки само. Основной генератор и редактор схемы - внешний агент, например Codex, Claude Code, opencode или другой инструмент, способный подключиться к приложению через предоставленный им интерфейс инструментов.

Роль приложения:

- импортировать конкретную версию CurseForge-модпака;
- извлекать данные, необходимые для отображения блоков с корректными текстурами и моделями;
- хранить локальную библиотеку модпаков и схем;
- показывать схему в 3D;
- позволять пользователю выделять области и оставлять change requests;
- предоставлять внешнему агенту контролируемый MCP-like интерфейс для чтения контекста и изменения схем;
- выполнять техническую валидацию команд агента;
- экспортировать готовые схемы в форматы Minecraft-экосистемы.

Продуктовый контракт первой версии: пользователь вставляет ссылку на CurseForge-модпак, выбирает релиз, получает рабочую локальную среду с блоками этого пака, просит внешний AI-инструмент создать или изменить схему, видит результат в приложении и экспортирует схему в выбранный формат.

## 2. Target User

Целевой пользователь первой версии - обычный игрок Minecraft, а не разработчик модов и не технический power user.

Следствия:

- интерфейс должен объяснять действия человеческим языком;
- приложение может требовать CurseForge API key, но должно понятно объяснять, зачем он нужен, где его получить, где он хранится и как его заменить;
- пользователь не должен вручную распаковывать модпаки, искать файлы ассетов или редактировать проектные файлы;
- пользователь не обязан понимать внутреннюю модель схемы, MCP или форматы модов;
- пользователь работает с приложением через библиотеку модпаков, схемы, 3D-preview, выделения, запросы на изменения и экспорт.

## 3. Platform And Distribution Requirements

Первая версия должна быть десктопным приложением.

Поддерживаемые платформы:

- Windows;
- macOS;
- Linux.

Приложение должно распространяться как обычное устанавливаемое приложение или пакет для каждой ОС. Конкретные форматы установщиков и механизм обновления не фиксируются в этой спецификации и должны быть выбраны позже вместе с техническим стеком и каналом распространения.

Приложение не должно требовать Minecraft account, Microsoft/Mojang login или установленный Minecraft. Оно не запускает Minecraft и не интегрируется с локальной установкой игры.

## 4. Local-First Data Model

Все данные первой версии хранятся локально на компьютере пользователя.

Приложение не требует:

- аккаунтов;
- облачной синхронизации;
- серверной коллаборации;
- ролей пользователей;
- телеметрии;
- автоматической отправки ошибок;
- внешней инфраструктуры для хранения проектов.

Сетевые обращения первой версии ограничены CurseForge/API и скачиванием файлов выбранного модпака.

Уже импортированные данные должны быть доступны локально настолько, насколько это позволяет выбранная реализация. Строгий offline-mode не является отдельным бизнес-требованием: сетевые функции нужны для добавления модпаков и получения данных CurseForge.

CurseForge API key должен храниться в системном защищенном хранилище, например Keychain, Credential Manager или аналогичном механизме выбранной ОС. Обычный config-файл не должен использоваться для хранения ключа.

## 5. Library Structure

Главная структура приложения - локальная библиотека импортированных модпаков.

В левом sidebar отображается двухуровневое дерево:

- импортированные модпаки;
- схемы внутри каждого импортированного модпака.

Импортированный модпак - это конкретный локальный экземпляр конкретного CurseForge-релиза. Он включает выбранный CurseForge modpack, Minecraft version, loader и release/version.

Схема всегда принадлежит одному импортированному модпаку и тем самым привязана к его конкретной версии.

Пользователь может:

- добавить CurseForge-модпак;
- переименовать локальное имя импортированного модпака;
- удалить импортированный модпак вместе со всеми схемами и локальным кэшем этого экземпляра;
- создать схему внутри модпака;
- переименовать схему;
- удалить схему с подтверждением.

Пользователь может добавить один и тот же CurseForge-модпак одной и той же версии несколько раз. Дубли разрешены. Если локальное имя совпадает, приложение добавляет цифровой постфикс, например `All the Mods 10 - 2.14.1 (2)`.

Пользователь также может добавить другую версию того же CurseForge-модпака как отдельный импортированный модпак в sidebar. Группировка разных версий под одним элементом не требуется.

## 6. First Launch And Settings

При первом запуске приложение показывает onboarding.

Onboarding должен включать:

- выбор языка интерфейса;
- инструкции по подключению внешнего AI-инструмента;
- настройку CurseForge API key.

Язык по умолчанию выбирается по языку системы. Пользователь может сменить язык в onboarding и позже в настройках.

Интерфейс первой версии должен поддерживать русский и английский языки.

Тема интерфейса первой версии - только темная.

Onboarding по AI integration должен показывать инструкции и ждать подключения агента. Если агент подключился, onboarding считается успешно завершенным. Пользователь может нажать `Skip` и продолжить без подключения, а затем настроить интеграцию позже в настройках.

Если пользователь пропустил onboarding и CurseForge API key не настроен, мастер добавления модпака должен отправить пользователя в настройки, а не просить ключ внутри мастера.

В настройках должны быть:

- экран AI integration;
- управление CurseForge API key;
- смена языка;
- возможность открыть папки данных/диагностики через системный файловый менеджер.

Встроенный технический log viewer не требуется.

Отдельная кнопка `Delete all local data` не требуется. Достаточно удаления отдельных модпаков и схем.

## 7. CurseForge Modpack Import

Основная пользовательская входная точка - поиск CurseForge modpack по названию с выбором проекта из результатов.

Первая версия поддерживает только CurseForge modpack projects. Отдельные mods, resource packs, shader packs или пользовательские наборы не входят в область v1. Backend может использовать URL страницы выбранного CurseForge modpack как стабильный внутренний идентификатор discovery/import path.

Мастер добавления модпака:

1. Пользователь вводит название CurseForge-модпака.
2. Приложение ищет модпаки через CurseForge API и показывает список найденных проектов.
3. Пользователь выбирает нужный проект.
4. Приложение получает доступные релизы.
5. Приложение показывает один список релизов с фильтрами по Minecraft version и loader.
6. По умолчанию выбран последний доступный релиз.
7. Пользователь выбирает конкретный релиз.
8. Приложение скачивает и индексирует модпак.
9. При успехе модпак появляется в sidebar.
10. При ошибке пользователь получает понятное сообщение.

Если CurseForge API key не настроен, пользователь направляется в настройки.

Выбор Minecraft version и loader реализуется как фильтрация релизов, а не как отдельная ручная настройка после выбора версии. Итогом выбора всегда является конкретный CurseForge file/release.

Если модпак нельзя корректно разобрать до уровня, необходимого приложению, импорт считается неуспешным целиком. Частично импортированные модпаки, placeholder-блоки и silent degradation не входят в v1.

После добавления модпак считается зафиксированным снимком выбранного релиза. Приложение не проверяет обновления уже добавленных модпаков и не предлагает обновить импортированный экземпляр до новой версии.

AI-агент также может инициировать добавление модпака через инструменты приложения. Агент не скачивает модпак сам и не получает прямой доступ к файловой системе приложения. Он вызывает предоставленный приложением tool, а приложение выполняет скачивание, хранение, индексацию и возвращает статус. Отдельное подтверждение в UI для такого вызова не требуется.

## 8. Scheme Model

Схема - основной рабочий артефакт внутри импортированного модпака.

Схему можно создать двумя способами:

- пользователь создает пустую схему через UI;
- внешний AI-агент создает схему через tools приложения.

При создании схемы задаются:

- название;
- размеры рабочей области по X/Y/Z.

Размеры по умолчанию: 64 x 64 x 64.

Схема содержит:

- размеры рабочей области;
- блоки с координатами;
- block identifiers и допустимые состояния;
- привязку блоков к этапам строительства или группе `Unassigned`;
- change requests, привязанные к выделениям;
- метаданные, нужные приложению и агенту для валидации, отображения и экспорта.

Приложение не предоставляет полноценный ручной редактор блоков. Без внешнего агента пользователь работает со схемой как viewer/reviewer/exporter.

Автосохранение выполняется после каждой успешной операции пользователя или AI-агента.

История изменений, undo, user-facing snapshots и резервные копии не входят в v1. Если агент сделал неверное изменение, он должен исправить схему следующей операцией.

Для защиты от повреждения данных реализация должна стремиться к атомарному сохранению и валидации записываемого состояния, но это не является пользовательской функцией истории или бэкапов.

## 9. 3D Viewer And Review Tools

Главная рабочая область схемы - 3D-viewer.

Пользователь должен уметь:

- открыть схему;
- смотреть 3D-представление блоков;
- переключать этапы строительства;
- выделить блок или область;
- увидеть координаты выделения;
- оставить change request к выделению;
- открыть список change requests;
- посмотреть общий список материалов;
- экспортировать схему.

Пользователь не должен уметь вручную строить схему как в Minecraft creative mode. Ручная постановка, удаление, замена и массовое редактирование блоков не являются основным пользовательским workflow и не входят в обязательную v1-функциональность.

Пользовательский каталог блоков не требуется. Приложение может иметь внутренний индекс блоков для рендера, валидации, экспорта и AI tools, но отдельный UI для просмотра всех блоков модпака не нужен.

Происхождение блока из конкретного мода может храниться для AI, валидации и диагностики, но не обязано показываться пользователю в обычном интерфейсе.

## 10. Construction Stages

Этапы строительства - обязательная часть схемы.

AI-агент может создавать и изменять этапы. Пользователь может переключаться между этапами в UI.

Этапы упорядочены. Основной режим просмотра - накопительный:

- выбран этап 1: видны только блоки этапа 1;
- выбран этап 2: видны блоки этапов 1 и 2;
- выбран этап 3: видны блоки этапов 1, 2 и 3.

Дополнительный режим может показывать будущие этапы полупрозрачными, но режим по умолчанию скрывает будущие этапы полностью.

Блоки без назначенного этапа разрешены и отображаются как группа `Unassigned`. Это позволяет агенту сначала сгенерировать структуру, а затем распределить блоки по этапам.

Экспорт всегда включает итоговую схему целиком, включая `Unassigned`. Этапы являются внутренней функцией приложения и не обязаны попадать в экспорт как отдельные файлы.

## 11. Change Requests

Change request - локальная заметка пользователя к выделенному блоку или области.

Change request всегда привязан к выделению. Общие запросы ко всей схеме пользователь формулирует во внешнем AI-инструменте, а не через UI приложения.

Change request содержит:

- выделение, к которому он привязан;
- текст пользователя;
- статус `pending` или `resolved`.

Приложение не уведомляет агента само. Change requests сохраняются, а агент может прочитать pending requests через tools, изменить схему и пометить request как resolved.

В UI должна быть простая панель change requests. Клик по request фокусирует соответствующую область в 3D-viewer.

Ответы агента, комментарии, обсуждения и сложные workflow статусов не входят в v1.

## 12. AI Integration

Приложение должно предоставлять внешний интерфейс инструментов для одного активного AI-клиента.

AI integration запускается автоматически при старте приложения. В основном интерфейсе должен быть небольшой индикатор статуса подключения: подключен или не подключен внешний клиент, и имя клиента, если оно известно.

В настройках должен быть экран `AI integration`, который показывает:

- статус интеграции;
- статус активного клиента;
- параметры подключения, если они нужны пользователю;
- инструкции для подключения Codex, Claude Code, opencode или аналогичных инструментов.

Приложение не включает LLM, не хранит ключи к LLM-провайдерам и не исполняет творческую генерацию само.

AI-агент получает полную свободу действий через инструменты приложения, но только внутри границ этих инструментов.

Минимальный набор возможностей tools:

- прочитать список импортированных модпаков;
- добавить модпак по CurseForge-ссылке и выбранному релизу;
- прочитать схемы внутри модпака;
- создать схему;
- переименовать или удалить схему;
- прочитать размеры и содержимое схемы;
- читать текущее выделение пользователя;
- читать pending change requests;
- пометить change request как resolved;
- ставить, удалять и заменять блоки;
- выполнять bulk-операции по областям;
- менять размеры схемы, если операция валидна;
- создавать и изменять этапы строительства;
- назначать блоки этапам;
- запускать техническую валидацию;
- получать список материалов;
- экспортировать схему в выбранный формат.

Подключение нескольких AI-клиентов одновременно не поддерживается. В v1 допустим только один активный внешний клиент.

Если агент отправляет некорректную операцию, приложение отклоняет команду целиком и возвращает структурированную ошибку. Частичное применение, silent skipping и автоматическое исправление некорректных данных не допускаются.

## 13. Validation

Валидация v1 ограничена технической корректностью схемы и операций.

Приложение должно проверять:

- блок существует в выбранном импортированном модпаке;
- указанное состояние блока допустимо;
- координаты находятся внутри размеров схемы;
- bulk-операция не нарушает границы схемы;
- структура схемы остается валидной после операции;
- экспортируемая схема может быть собрана в выбранный формат.

Приложение не обязано проверять:

- работает ли механизм как в Minecraft;
- корректно ли подключены трубы, кабели, энергия или жидкости;
- правильно ли собраны multiblock structures;
- есть ли физическая поддержка у блоков;
- является ли постройка эстетически хорошей;
- является ли решение агента игровым или эффективным.

Уровень понимания поведения модовых блоков является отдельной темой исследования для будущих этапов. V1 не обещает симуляцию работы модов.

## 14. Materials List

В приложении должен быть общий список материалов для схемы.

Список материалов показывает:

- тип блока;
- количество блоков этого типа в текущей схеме.

Список материалов по этапам не является обязательным требованием v1.

## 15. Export

Пользователь может экспортировать итоговую схему через стандартный save dialog, выбирая место сохранения и имя файла.

Форматы экспорта v1:

- Litematica `.litematic`;
- Sponge/WorldEdit `.schem`.

Minecraft structure `.nbt` не входит в v1.

Пользователь должен сам выбирать формат экспорта. Экспорт по умолчанию включает всю итоговую схему, включая блоки из `Unassigned`.

Импорт существующих `.litematic`, `.schem` или `.nbt` схем не входит в v1.

## 16. UI Requirements

Общий UI:

- одно главное окно/workspace;
- sidebar с импортированными модпаками и схемами;
- основная область 3D-viewer;
- панель или область change requests;
- доступ к materials list;
- доступ к export action;
- индикатор AI connection;
- настройки.

Multi-window, tabs для нескольких открытых схем, совместное редактирование и ручной CAD-like editor не входят в v1.

Пустое состояние:

- при первом запуске показывается onboarding;
- после завершения или пропуска onboarding пустая библиотека показывает empty state с кнопкой добавления CurseForge-модпака.

Отдельная встроенная help/FAQ не требуется. Достаточно onboarding и настроек с понятными инструкциями.

## 17. Explicit Non-Goals For V1

В первую версию не входят:

- встроенная AI-модель;
- встроенный AI-чат как основной способ работы;
- ручной Minecraft creative-like editor;
- пользовательский каталог всех блоков;
- импорт существующих схем;
- resource packs и shader packs сверх выбранного модпака;
- отдельные mods вместо modpack pages;
- Minecraft login;
- запуск Minecraft;
- облачная синхронизация;
- серверная коллаборация;
- роли и аккаунты;
- телеметрия и аналитика;
- автоматические crash reports;
- проверка обновлений импортированных модпаков;
- автообновление приложения как зафиксированное бизнес-требование;
- undo и история изменений;
- пользовательские резервные копии;
- встроенный technical log viewer;
- полная симуляция поведения модовых блоков.

## 18. Deferred Research Topics

Эти темы важны, но не должны блокировать высокоуровневую продуктовую спецификацию.

### 18.1 Modpack Parsing Feasibility

Нужно исследовать реальные CurseForge-модпаки и понять, какие данные стабильно извлекаются:

- blocks;
- blockstates;
- models;
- textures;
- item/block names;
- loader-specific differences;
- Minecraft-version-specific differences.

Результат исследования должен уточнить технические ограничения импорта и критерии "модпак корректно разобран".

### 18.2 Behavior Understanding

Поведение модовых блоков не фиксируется как v1-обязательство.

Нужно отдельно исследовать, можно ли без чрезмерного усложнения извлекать полезные сведения из файлов модпака:

- lang files;
- tags;
- recipes;
- configs;
- guidebook/Patchouli-like content, если оно есть в модпаке.

Это может стать optional AI context layer, но приложение не должно превращаться в скрытого агента или симулятор модов.

Внешние wiki, GitHub, source scraping и документация модов не входят в v1, потому что сетевые обращения первой версии ограничены CurseForge/API и скачиванием модпака.

### 18.3 Update Mechanism

Механизм обновления самого приложения нужно выбрать позже после выбора стека и канала распространения.

### 18.4 Export Fidelity

Нужно подтвердить, какие данные выбранных форматов `.litematic` и `.schem` позволяют сохранить для модовых блоков, block states и metadata, и какие ограничения должны быть показаны пользователю или агенту.

## 19. Success Criteria

Первая версия считается успешной только если выполняются все три условия:

1. Пользователь вставляет CurseForge-ссылку, выбирает релиз, и приложение импортирует модпак с реальными блоками, моделями и текстурами.
2. Внешний AI-агент подключается к приложению и может создавать или изменять схемы через предоставленные tools.
3. Пользователь экспортирует готовую схему в `.litematic` или `.schem`, и результат открывается в целевом Minecraft-инструменте.

Дополнительные признаки успешности:

- обычный пользователь понимает onboarding и настройки без чтения внешней технической документации;
- некорректные операции агента отклоняются целиком и возвращают полезные ошибки;
- схемы автосохраняются после успешных операций;
- этапы строительства позволяют пользователю смотреть схему накопительно;
- change requests позволяют пользователю указать агенту конкретное место, которое нужно переделать.
